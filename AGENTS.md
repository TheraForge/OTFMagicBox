# AGENTS.md

## Project Structure & Module Organization

This repository contains the TheraForge MagicBox iOS app, its watchOS companion, tests, a local Swift macro package, and GitHub Actions automation.

- `OTFMagicBox.xcworkspace` is the normal entry point because CocoaPods are used.
- `OTFMagicBox.xcodeproj` defines the app targets `OTFMagicBox`, `OTFMagicBoxTests`, and `OTFMagicBoxWatch`.
- `OTFMagicBox/` contains the iOS app. App startup lives in `App/AppEntry`; shared services live in `Managers`, `Network`, `Navigation`, `UI`, and `Utilities`.
- `OTFMagicBox/Features/<Feature>/` is the usual home for feature code, organized into `Screens`, `ViewModels`, `Models`, `Components`, `Helpers`, `Controllers`, or `Coordinators` as needed.
- `OTFMagicBox/Features/*/Models/*Configuration.yml` files drive much of the app copy and feature behavior. Keep Swift models, fallback values, and YAML schema changes in sync.
- `OTFMagicBox/Assets.xcassets`, `OTFMagicBox/Samples.xcassets`, `OTFMagicBox/Base.lproj`, and `OTFMagicBox/MagicBox.icon` hold app resources.
- `OTFMagicBoxWatch/` contains watchOS app, feature, manager, service, extension, asset, and entitlement files.
- `OTFMagicBoxTests/` contains app tests and shared helpers in `TestSupport.swift`.
- `RawGenerableMacro/` is a local Swift Package with `RawModel`, `RawGenerableMacros`, and `RawGenerableMacroTests`.
- `Snippets/` and `Scripts/install_snippets.rb` provide ResearchKit Xcode code snippets.
- `.github/workflows/` and `.github/scripts/` contain testing and TestFlight deployment automation.

## Build, Test, and Development Commands

Open the workspace, not the project:

```sh
open OTFMagicBox.xcworkspace
```

Install or refresh CocoaPods dependencies:

```sh
pod install
```

Inspect available schemes and targets:

```sh
xcodebuild -list -workspace OTFMagicBox.xcworkspace
xcodebuild -list -project OTFMagicBox.xcodeproj
```

Build the iOS app scheme:

```sh
xcodebuild -workspace OTFMagicBox.xcworkspace -scheme OTFMagicBox -destination 'platform=iOS Simulator,name=iPhone 17 Pro,OS=26.5' build
```

Run the app test suite with coverage, matching the README coverage workflow:

```sh
xcodebuild test -workspace OTFMagicBox.xcworkspace -scheme OTFMagicBox -destination 'platform=iOS Simulator,name=iPhone 17 Pro,OS=26.5' -enableCodeCoverage YES -resultBundlePath /tmp/OTFMagicBox-coverage.xcresult
xcrun xccov view --report --only-targets /tmp/OTFMagicBox-coverage.xcresult
ruby Scripts/generate_coverage_badge.rb /tmp/OTFMagicBox-coverage.xcresult
```

Run the local macro package tests:

```sh
swift test --package-path RawGenerableMacro
```

Run lint explicitly before submitting changes:

```sh
swiftlint lint --no-cache
```

Install ResearchKit Xcode snippets when needed:

```sh
ruby Scripts/install_snippets.rb
```

CI uses `.github/scripts/test_app.sh` for `OTFMagicBox` tests. `.github/workflows/Testing.yml` runs on pushes to `development`; `.github/workflows/Deploying.yml` deploys from `main`.

## Coding Style & Naming Conventions

Swift uses four-space indentation and the existing MARK-separated style. Preserve the Hippocrates copyright header in files that already have it.

Follow existing names: `*View` for SwiftUI screens, `*ViewModel` for observable state, `*Configuration` plus matching `*Configuration.yml` for YAML-backed settings, `*Manager` for shared services, `*Coordinator` for navigation/auth flows, and `Type+Extensions.swift` for extensions. Prefer feature folders before adding shared code.

SwiftLint is configured in `.swiftlint.yml` and runs as an Xcode build phase. Pods, build products, and package build folders are excluded.

## Testing Guidelines

The primary app test target is `OTFMagicBoxTests`. Tests use Swift Testing (`import Testing`, `@Suite`, `@Test`, `#expect`, `#require`) and run through the `OTFMagicBox` scheme. Test files are named by area, such as `ScheduleAndCheckUpDomainModelTests.swift`, `WatchAuthSessionStoreTests.swift`, and `CloudantSyncPolicyTests.swift`.

Use `OTFMagicBoxTests/TestSupport.swift` for shared fakes, isolated `UserDefaults`, publisher awaiting, and notification helpers. Prefer deterministic tests with injected clocks, calendars, decoders, stores, and closures.

Coverage is documented in `README.md`. The badge lives at `badges/coverage.svg` and is generated by `Scripts/generate_coverage_badge.rb`, defaulting to the `OTFMagicBox.app` coverage target. Whenever test targets are added, removed, renamed, or significantly reorganized, update the coverage badge and any related coverage documentation or scripts so they continue to reflect the current test configuration.

## Commit & Pull Request Guidelines

Recent commits use short, imperative summaries, usually without scopes or issue IDs: examples include `Add manual test coverage badge`, `Address PR review test feedback`, and `Expand health card unit coverage`. Follow that style unless a branch or issue requires more structure.

Before opening a PR, run relevant local checks: SwiftLint, `swift test --package-path RawGenerableMacro` for macro changes, and `OTFMagicBox` Xcode tests for app behavior. Include test evidence, coverage badge updates when applicable, screenshots for UI changes, and notes for YAML schema, signing, entitlement, or migration changes. PR review expectations beyond this are not currently documented.

## Architecture Overview

MagicBox is a SwiftUI app with UIKit and ResearchKit/CareKit bridges where needed. `OTFMagicBoxApp` creates `AppRuntime`, which injects configuration, user defaults, notifications, network setup, auth/session actions, app lock presentation, and foreground sync hooks. Shared managers handle Cloudant sync, HealthKit, CareKit stores, sessions, keychain/cloud user data, outcomes, uploads, and activity.

The app is configuration-heavy: app-wide settings live in `OTFMagicBox/App/Configurations/AppConfiguration.yml`, style in `OTFMagicBox/App/Styles/StyleConfiguration.yml`, and feature-specific settings under each feature’s `Models` folder. Extend existing loaders, fallback values, and tests together.

## Security & Configuration Tips

Do not commit real API keys, signing certificates, provisioning profiles, tokens, or user data. `AppConfiguration.yml` contains a dummy `apiKey`; real TheraForge keys should be handled through secure project setup. Signing and TestFlight secrets are referenced from GitHub Actions secrets in `.github/workflows/Deploying.yml` and helper scripts under `.github/secrets/`.

Avoid modifying bundle identifiers, entitlements, signing teams, provisioning scripts, or TestFlight settings unless explicitly requested. `build/`, `DerivedData/`, `.build/`, `Pods/`, archives, `.ipa`, and dSYM files should stay out of source control.

## Agent-Specific Instructions

Make minimal, targeted changes that follow existing folders and names. Update Swift tests when behavior changes, and update YAML fixtures, fallbacks, snippets, generated files, or the coverage badge when related targets or configuration change. Run relevant build, test, lint, and coverage commands before finishing when practical. Do not introduce dependencies, alter signing, change bundle identifiers, edit entitlements, or adjust CI release settings without explicit approval.
